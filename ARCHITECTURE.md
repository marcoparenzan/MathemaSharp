## Typed interoperability — current state

MatSharp keeps `GenericScalar<T>` as real 2D column-major storage. The runtime exposes a registration for left division, separate from the kernels; the `MatSharpLib.NDSharp` module registers adapters for Half, float, double and Decimal32/64/128. The registration is static per type and keeps the first adapter: it is not a different policy for each interpreter instance. The solver copies the data into T, reuses LU on the square ones and calls QR for each RHS of the overdetermined ones. Underdetermined ones are rejected, not solved with an approximate formula.

PySharp distinguishes `ClrType`, `ClrObject` and `ClrMethod`. `ClrBinder.SelectGenericType` closes a definition through MakeGenericType and checks arity/constraints; GetItem applies the binder to ClrType. The tests verify the types injected by the host and a Decimal128 list; they do not certify universal import, inference or marshalling.

## Type map

| Type | Model / indicative precision | Use and caveats |
|---|---|---|
| byte…long, UInt128/Int128 | Fixed-width integers | Exact within the range; decide checked or wrap |
| BigInteger | Arbitrary-precision integers | Exact, limited by memory/time; possible allocations |
| Half | IEEE binary16, about 3 decimal digits | Compact storage; accumulation errors important |
| float | IEEE binary32, about 6–9 digits | Graphics, compact data |
| double | IEEE binary64, about 15–17 digits | General scientific computing |
| decimal | 96-bit coefficient × 10^-scale, scale 0–28 | 28–29 digits; finance with explicit policy; overflow/division by zero raise exceptions |
| Complex | Two doubles | Unordered, phase in radians, branch cuts in the complex functions |
| Decimal32 (.NET 11) | IEEE decimal, 7 significant digits | 32 bit; NaN, infinity, signed zero, variable exponent |
| Decimal64 (.NET 11) | IEEE decimal, 16 significant digits | 64 bit; not equivalent to double |
| Decimal128 (.NET 11) | IEEE decimal, 34 significant digits | 128 bit; not equivalent to System.Decimal |
| Complex<T> (.NET 11) | Two T components | T: IFloatingPointIeee754<T>, IMinMaxValue<T>; also IEEE decimal, not System.Decimal |

Significant digits are not places after the decimal point. Base 10 represents 0.1, but not 1/3. More precision does not eliminate algorithmic errors nor imply greater performance. `double.Epsilon` is the smallest positive subnormal; ULP at 1 is about 2.22e-16. NaN/infinity must be handled according to the application domain.

## Generic Math: choosing the constraint

- Static abstract interface members allow operators and constants on T without `dynamic`, reflection or mandatory boxing.
- `INumberBase<T>`: sum, product, Horner; also accepts Complex.
- `INumber<T>`: orderable numbers, Min/Max/Clamp; do not use it for an algorithm that must accept Complex.
- `IBinaryInteger<T>`: GCD, bits and integer division.
- `IFloatingPoint<T>`: fractional mean and rounding; includes decimal.
- `IFloatingPointIeee754<T>`: Kahan here, NaN, infinity, scientific functions; does not include System.Decimal.
- New `IDecimalFloatingPointIeee754<T>` in 11: IEEE decimal specific operations.
- `CreateChecked`, `CreateSaturating`, `CreateTruncating`: conversion policies, not promises of absence of loss of precision in floating-point conversions.

Generic Math reuses algorithms, it does not guarantee associativity, stability, vectorisation or all the mathematical identities in finite arithmetic.

## Numbers and NDSharp

NDSharp (PySharp repository, package 2.5.0) is an ndarray with NumPy semantics: runtime dtype, strided views, broadcasting, linalg, FFT, PCG64 random. Numbers is the typed layer: Generic Math and `Span<T>`, compile-time checks, no dependencies. It was decided **not to merge** the two libraries: they have different contracts (dynamic versus static dtype). `MathemaSharp.NDSharp` connects them:
- towards Numbers it copies in C order with a cast, because strided views cannot be exposed as a Span;
- towards NDSharp it wraps a `double[]` without copying.

The current duplications (QR in `MathemaSharp.LinearAlgebra.MatrixAlgebra`, didactic DFT in Core against NDSharp's FFT) are small and intentional. If they grow, they must be extracted into a common core: it is a decision to take when the duplication becomes real.

## Contracts of the algorithms

Empty sum = Zero. Dot on different lengths raises ArgumentException; generic Complex dot is bilinear, HermitianDot conjugates on the left. Horner uses increasing coefficients; empty polynomial = Zero. Empty mean not defined. GCD(0,0)=0; Abs(MinValue) signed can overflow. Factorial accepts n>=0, with no guarantees of cost for huge n. Kahan is didactic for finite data, not a universal exact reduction. Forward DFT unnormalised O(N²); empty array produces empty output. SIMD handles the tail but reorders the accumulation. InvoiceTotal distinguishes per-line rounding from the total; it does not implement VAT/exchange or tax regulations.

### Where double remains, and why

| Source | Boundary | Consequence / action |
|---|---|---|
| NDArrayBridge.cs:15–27, 43–59, 73–77 | NDArray → double → T; T → double → float64 | Potential loss of digits, range and dtype. Priority: native dtype mapping and explicit conversions |
| NDArrayBridge.cs:34–39, 65–70 | Non-generic Complex ↔ Complex<double> | Does not preserve a Decimal128 component; design a separate adapter |

## Linear system diagnostics

Separate opt-in API `LinearSystemDiagnostics.Solve<T>(A,b)` and record `LinearSolveReport<T>`, IEEE constraint. Keeps the existing LU Solve unchanged. Returns solution, ||Ax−b||∞/||b||∞, backward error ||Ax−b||∞/(||A||∞||x||∞+||b||∞), approximate infinity condition number and reciprocal. `NormwiseBackwardError` is an alias of `NormwiseBackwardErrorInfinity`.

A and vectors are scaled separately; residual accumulated with FMA in T. It serves to avoid many intermediate overflows, not to compute the exact residual: rounding and underflow can remain and an exact solution can have a non-zero measured residual. Zero rhs and zero residual have zero indicators. Non-representable solutions/intermediates are flagged.

ConditionInfinityEstimate uses ||Abar||∞ and n columns of the normalised inverse obtained with the same LU; it keeps only the row sums, not a complete inverse matrix. Cost n additional solves, O(n²) memory for normalised data. It is a norm of the approximate inverse, not an iterative LAPACK estimator, a rigorous bound or an estimate of the conditioning of the single components. If the estimate overflows, condition=+infinity and rcond=0; if the columns are not representable, explicit error.

IsIllConditioned flag: rcond ≤ sqrt(epsilon), a warning policy of potential loss of at least half of the digits. False does not certify accuracy; true does not imply that every right-hand side will give an inaccurate solution. Tests on six formats, zero rhs, scales 1e±200, wrong inputs, Hilbert condition against mpmath and Hilbert12 with small residual but warning true. Decimal128 Hilbert8 does not trigger the flag thanks to the different epsilon: it is not a universal judgement on the dataset.

Notebook LinearAlgebra/13-solve-diagnostics run; four References regenerated to include the new types. It does not run refinement and does not estimate the true forward error without an independent reference.

DiagonalizeHermitian2 — distinct consolidation: verifies finite components and Hermiticity, global scale, Hypot radius, no absolute threshold 1e-12 for the coupling. The eigenvector branch chooses radius+abs(halfDiff) and builds the second vector as an orthonormal complement; zero and identity have independent bases. Out-of-range eigenvalues throw ArithmeticException. Eight NativeHermitianTests cover all six formats, complex components, residuals on the normalised matrix, scales MaxValue/4 and T.Epsilon, Decimal128 coupling 1e-25 and wrong inputs. The phases of the eigenvectors can change. Limits remain: normalisation can cancel extremely small components with respect to the scale and mean±radius can cancel the small eigenvalue in very unbalanced spectra; it is not a general solver.
